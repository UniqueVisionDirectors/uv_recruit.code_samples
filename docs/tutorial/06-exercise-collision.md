# 【問題②】並列で壊れる：衝突を観測する

前章で、ステージ1の実装を **3台** に並べました。<br>
同じ実装を複数台で動かしても、ID発行はまだ正しく動くでしょうか？　実際に試してみましょう。

## 大量のアクセスを浴びせる

ブラウザで web（<http://localhost:5173>）を開きます。<br>
「ジョブ起動」から、**負荷ランナー** を使ってまとめてID発行を行えます。

次のように設定して「起動」します。

- **ターゲット**：`lb`（3台の app に振り分ける入口）
- **N**：作るIDの件数（例：2000）
- **並列度**：同時に投げるリクエスト数

まず **並列度 1** で起動してみましょう。<br>
ジョブ一覧から詳細を開くと、`conflict_count`（衝突回数）が **0** で、すべて作れているはずです。

## 並列度を上げると…

次に、**並列度を 100、1000** と上げて、同じように起動してみてください。<br>
ジョブ詳細の `conflict_count` を見ると、**0 より大きい値**（＝衝突）が現れることがあります。

::: warning 衝突の回数は実行ごとに変わります
実機での衝突は **負荷やタイミングに左右され、0 のこともあります**。<br>
並列度を上げるほど起きやすくなりますが、「必ず何回」と決まった数にはなりません。<br>
（確実に再現して確かめる方法は、次の章で扱います。）
:::

## なぜ衝突するのか

衝突が起きると、DB が「そのIDはもう使われている」と重複を拒否し、API は **409（Conflict）** を返します。<br>
負荷ランナーは、この 409 の回数を `conflict_count` として数えています。

では、なぜ同じIDが2回作られてしまうのでしょうか。

- 3台のサーバーは、**互いの存在を知らずに**、それぞれ独立してIDを作ります。
- しかも各台は **同じロジック**・**同じ番号の空間** から選びます（同じミリ秒なら、取りうる連番の範囲は同じ）。
- 各台は **ランダムな位置** から数え始めるので、別々の台が選んだ範囲が **偶然重なる** と、同じIDが2回作られて衝突します。

1台のときは、自分が作ったIDを `counter` で覚えていたので重複を避けられました。<br>
しかし3台は、互いを **区別する手段がない** ため、これを防げません。

では ―― **3台が互いを知らないまま、それでも重複しないIDを作る** には、どうすればよいでしょうか？<br>
