# 【問題②】並列で壊れる：衝突を観測する

前章で、ステージ1の実装を **1台（app）** と **3台（lb）** に並べました。<br>
同じ実装でも、**台数が変わると** ID発行の結果は変わるのでしょうか？　実際に負荷をかけて確かめます。

ブラウザで web（<http://localhost:5173>）を開き、「ジョブ起動」を使います。<br>
ここでは **負荷ランナー** が、指定した件数のID発行を並列でまとめて実行し、`conflict_count`（衝突回数）を数えてくれます。

設定項目は3つです。

- **ターゲット**：負荷をかける先。`app（1台）` と `lb（3台・LB経由）` を選べます。
- **N**：作るIDの件数（例：2000）
- **並列度**：同時に投げるリクエスト数

## まず1台（app）に浴びせる

最初に **ターゲット＝`app（1台）`** で、並列度を **1 → 100 → 1000** と上げながら起動してみてください。<br>
ジョブ詳細を開いても、`conflict_count` は **どれだけ並列度を上げても 0 のまま** です。

なぜでしょうか。`app` は **1台（1プロセス）** で動いています。<br>
ステージ1で実装した発行ロジックは、自分が配った連番を `counter` で覚えていて、同じ1台の中ではそれを使い回しません。<br>
リクエストがどれだけ同時に来ても、1台の中では **順番に番号が振られる** ので、**1台のうちは衝突しようがない** のです。<br>
これが「ステージ1の実装は **1台なら正しい**」という意味でした。

## 次に3台（lb）に浴びせる

では **ターゲット＝`lb（3台・LB経由）`** に切り替えて、並列度を **100、1000** と上げてみましょう。<br>
今度はジョブ詳細の `conflict_count` に、**0 より大きい値**（＝衝突）が現れることがあります。

::: warning 実機での衝突は確率的です
実機での衝突は **負荷やタイミングに左右され、0 のこともあります**。<br>
並列度を上げるほど起きやすくなりますが、「必ず何回」と決まった数にはなりません。<br>
（確実に再現する方法は、この章の最後で扱います。）
:::

## なぜ衝突するのか

衝突が起きると、DB が「そのIDはもう使われている」と重複を拒否し、API は **409（Conflict）** を返します。<br>
負荷ランナーは、この 409 の回数を `conflict_count` として数えています。

では、なぜ同じIDが2回作られてしまうのでしょうか。

- 3台のサーバーは、**互いの存在を知らずに**、それぞれ独立してIDを作ります。
- しかも各台は **同じロジック**・**同じ番号の空間** から選びます（同じミリ秒なら、取りうる連番の範囲は同じ）。
- 各台は **ランダムな位置** から数え始めるので、別々の台が選んだ範囲が **偶然重なる** と、同じIDが2回作られて衝突します。

1台（`app`）のときは、自分が作ったIDを `counter` で覚えていたので重複を避けられました。<br>
しかし3台（`lb`）は、互いを **区別する手段がない** ため、これを防げません。<br>
いま見ている衝突は、**「複数台になった瞬間」に初めて現れる** 問題なのです。

## 確実に衝突を見せる

ライブの負荷観測は、上で見たとおり **確率的** で、0 のこともありました。<br>
そこで、**同じミリ秒を強制** して、素朴解（サーバーを区別しないステージ1のロジック）が **必ず** 衝突することを、決定的に確かめるテストがあります。

```bash
docker compose run --rm app uv run pytest tests/test_idgen_collision.py::test_stage1_naive_collides_across_processes -v
```

このテストは、**互いを知らない2つの発行器** が同じミリ秒に **4096件ずつ（計8192件）** を発行する状況を再現します。<br>
1台あたりの番号は 4096通りしかないので、8192件を作れば **鳩の巣原理により必ず衝突** します ―― 実機の運に左右されず、**いつでも緑（＝衝突を再現）** になります。

::: tip これは「素朴解の弱点」の証明です
このテストが見ているのは、解答例の **素朴解（ステージ1）そのものの性質** です。<br>
あなたの実装の採点ではなく、「サーバーを区別しないロジックは複数台で必ず破綻する」ことを示すためのものです。<br>
（あなた自身の実装の確認は、ステージ1なら `pytest -m exercise` で済ませました。）
:::
