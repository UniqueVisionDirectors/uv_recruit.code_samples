# ユーザーID発行API 教材 — 設計（目的・要件の言語化）

> 作成日: 2026-06-28
> 位置づけ: 本プロジェクトの **目的そのものの再定義**。今後の作業（実装計画・実装）の土台となる上位ドキュメント。
> 既存の `fastapi-postgres-docker` / `vscode-devcontainer` の各設計が用意した **インフラ（FastAPI / PostgreSQL / Docker / uv）はそのまま土台として再利用**し、アプリの題材を「汎用 `Item` CRUD」から「ユーザーID発行」へ置き換える。

---

## 1. 目的

**Web アプリケーションの仕組みを理解するための初心者向け教材**。

題材は **ユーザーID発行 API**（ユーザー登録時にIDを払い出す API）。単にAPIを動かすことが目的ではなく、

> 「素朴な実装は、サーバーをスケールさせるとなぜ壊れるのか／どう直すのか」

を、学習者が**手を動かして**・**数で**理解することを狙う。

## 2. カリキュラム（2ステージ）

### ステージ1 — ID発行ロジックを書く
- エンドポイント（HTTPの受け口・リクエスト/レスポンスの器）は**教材が提供**する。
- 学習者が書くのは **ID発行ロジック `issue_user_id(...)` の中身だけ**（穴埋め式）。
- 単一サーバーで正しく動き、ステージ1のテストが通ることがゴール。

### ステージ2 — 並列化しても衝突しないようにする
- ロードバランサ配下に app を**複数レプリカ**で稼働させる（`docker compose up --scale app=N` を想定）。
- ID発行の要求者は、背後のサーバー構成を**一切意識しない**（LBの後ろのAPIサーバーと同じ要領）。
- 学習の流れ（「壊れる→直す」アーク。ステージ1自由度の方針は **(C) ハイブリッド**）：
  1. ステージ1の素朴解を並列稼働させ、**ID衝突が実際に起きる様子を観測**する。
  2. **なぜ・どれくらいの試行で衝突するのか**を定量的に分析する（本教材の山場。第5章）。
  3. **アプリケーション（サーバー）側のロジック**で一意性を保証して直す。
- 制約：**PostgreSQL のトランザクションによる一意性保証は採らない**。毎リクエストでDBを調停役にするとDBがボトルネックになるため。一意性は**アプリ側**で担保する。

## 3. IDの要件（確定）

| 項目 | 要件 |
|---|---|
| 文字種 | **base62**（`0-9A-Za-z`、記号なし） |
| 長さ | **10文字** |
| 整列性 | **発行順にソート可能**。素朴な文字列ソート（`ORDER BY id` / `sorted()`）で「2つのIDのどちらが若いか」を判定できる。絶対的な“何番目か”は不要（相対順序のみ） |
| 予測困難性 | **連番を避ける程度で十分**。生成アルゴリズムを知っていれば「ありうるID／ありえないID」を予測できても構わない（強い秘匿性は不要） |
| 最大総発行数 | **10^10（100億）以上**（人類全員に発行しても余る規模。本設計の理論上限 `≈5.76×10^17` で大幅に充足） |
| 時刻解像度 | **ミリ秒** |

### 補足：文字種を base62（記号なし）にした理由
- 「発行順ソート」を**素朴な文字列ソート**で満たすには、文字集合が **ASCII順＝値順**に並んでいる必要がある。`0-9A-Za-z` はこの条件を満たす（`0x30–0x39 < 0x41–0x5A < 0x61–0x7A`）ため、`ORDER BY id` だけで時刻順になる。
- 記号（`-` `_` 等）は ASCII 上で英数字の前後に散らばり、混ぜると素朴ソートが崩れ「時刻成分をデコードして比較」という一手間が要る。容量は base62 で十分（10^10 要件に対し8桁の余裕）なので、**記号は採用しない**。

## 4. ID構造（確定）

10文字 base62 の全空間は `62^10 ≈ 8.39×10^17 ≈ 2^59.46`。これを次のように配分する（合計59bit、上限内に収まる）。

| フィールド | bit | 役割・容量 |
|---|---|---|
| ミリ秒タイムスタンプ | 41 | あるエポックから **約70年**（`2^41 ms ≈ 69.7年`）運用可能。ソートの基準 |
| **worker-id** | 6 | 最大 **64 インスタンス**並列。**ステージ2の修正点そのもの** |
| 同ミリ秒内シーケンス | 12 | **4,096 件/ms/台**（≈ 約410万/秒/台、全64台で約2.6億/秒）。予測困難性は「毎msランダムな開始位置から始まるカウンタ」等で連番性を消す |

- **最大総発行数**：理論上 `≈5.76×10^17`。要件 10^10 を大幅に充足。
- **エンコード**：`値 = ms × 2^18 + worker_id × 2^12 + sequence` を base62 で10文字に固定長エンコード（ゼロ詰め）。値順 = 文字列順となるよう、上位フィールドほど時刻成分にする。

### なぜこの制約が教材として優れているか
- 「10文字」「ソート可能（先頭=時刻）」という制約が、ステージ1の素朴解を**観測可能な衝突モード**へ追い込む（第5章）。
- worker-id（6bit）の有無が、そのまま**ステージ1とステージ2の差分**になっている。抽象レベルで「素朴解＝worker-id無し」「正解＝worker-id有り」と対称的に説明できる。

## 5. ステージ2の核心：衝突は「現実的な時間で観測可能」か

本教材の成否を分ける論点。**衝突が astronomically rare な誕生日衝突だと、デモで観測できず教材が成立しない。** 制約を逆手に取り、衝突を観測可能にする。

### 5.1 反例：UUIDv7-hex を10文字に詰める案は観測**不能**
- hex（文字種16）の全空間は `16^10 = 2^40 ≈ 1.1×10^12`。ソート用にミリ秒タイムスタンプ（約70年で41bit）を載せようとすると**40bitに収まりすらしない**。
- base62 に広げ、乱数を温存して10文字に詰めた場合でも、全空間 `2^59.5` に対し50%衝突は約 `2^29.7 ≈ 8.7×10^8` 件。毎秒1万件でも**約24時間**。→ デモでは事実上観測不能。

### 5.2 本教材の素朴解は「構造的に」衝突する
- ステージ1の素朴解は **worker-id を持たない**（`ms + シーケンス` のみ）。各プロセスが**独立にシーケンスを採番**する。
- 2レプリカが**同一ミリ秒**で発行すると、`(ms, sequence)` が一致し得る。とくにシーケンスが「各プロセスで0から始まるカウンタ」だと、**確率の問題ですらなく構造的に**衝突する（両プロセスの“そのms最初の1件”が `(ms, 0)`）。
- → 軽い並行負荷で**数秒以内**に重複IDを再現できる。
- 仮に学習者がシーケンスを**18bit乱数**にしても、同ms内の誕生日衝突により、5.1のUUIDv7温存型（約24時間）とは桁違いに早く衝突する。**「自分の方式は何回の試行で衝突するか」を見積もる定量分析を必修**にして、観測可能性の理屈を学ばせる。

### 5.3 修正：worker-id の静的付与
- 各レプリカに、**起動時に一度だけ** distinct な worker-id を付与する（6bit、最大64台）。
- 付与方法は「**毎リクエストの調停を伴わない**」ことが肝。コンテナのレプリカ番号（hostname の序数）から導出、または明示的な環境変数。
  - `docker compose up --scale app=N` ではレプリカごとに個別の環境変数を与えにくいため、**hostname の序数から導出**する方式を本命とする（詳細な確実性は実装計画で詰める）。
- これにより `(ms, worker_id, sequence)` が**原理的に衝突不能**となり、**DBを毎回触らずに**一意性を保証できる。これが本教材の主張「DBをボトルネックにせずアプリ側で一意性を保証する」の到達点。

## 6. リポジトリ構成（方針）

`Item` CRUD は撤去し、ユーザーID発行に一本化する。**出題用API と 解答例API を両方リポジトリに併置**する（学習者は出題用を実装し、解答例と見比べられる。カンニング可だが試験ではないので許容）。

- **共通コアを共有し、ID発行ロジックだけ差し替える兄弟構成**とする（DRY＝知識の重複を排除しつつ、出題/解答を対称に扱う）。
  - 共有: User モデル / DB セッション / スキーマ / エンドポイントの結線。
  - 差分: `issue_user_id` の実装だけ（出題用＝`NotImplementedError` のスタブ、解答例＝ステージ1/ステージ2の実装）。
- 想定する実行単位（詳細な配置・サービス名は実装計画で確定）：
  - 出題用アプリ（学習者が編集）。
  - 解答例アプリ（ステージ1・ステージ2の参照実装）。
  - ステージ2のデモは、対象アプリを `--scale` で複数レプリカ稼働させて衝突観測→修正後の不衝突を確認する。

## 7. テスト方針（仕様＝テスト）

- **テストが仕様書を兼ねる**。学習者はテストを実行して自分の `issue_user_id` 実装の正しさを確認する。
- ステージ1テスト（単一サーバー）：形式（base62・10文字）、発行順ソート、単一プロセスでの一意性。
- ステージ2テスト（並列）：複数レプリカ／複数プロセスで大量発行し、**重複がないこと**を検証。素朴解では**意図的に衝突が観測される**こと（壊れる確認）も教材の一部として扱う。

## 8. 設計原則との対応（CLAUDE.md）

- **KISS / YAGNI**：題材を `Item` から User 一本に絞る。worker-id 付与は静的（毎リクエスト調停・外部コーディネータなし）。
- **DRY＋直交性**：出題/解答で重複する「コードの見た目」ではなく、共有すべき「知識」（モデル・DB・結線）だけを共通化し、差分（発行ロジック）は分離する。
- **対称性**：出題用/解答例、素朴解/正解（worker-id 無し/有り）を、抽象レベルで同種のものとして対称に表現する。差（worker-id の有無）は、並列下の一意性という**実際の差異**を反映している。
